## BLOCKER (1)

### B1 — Editing an already-set string or colour property writes nothing. The new editable string field is dead for exactly the fields a document has.
`src/editor/schema-panel.ts` ~410–419 · `src/editor/ensemble-editor.ts:3768` · lens: correctness · **confirmed**

The new fallback branch is the only branch in `schemaWidgets` that never consults `bound`:

```ts
ui.inputField({
  value: value === undefined || value === null ? '' : String(value),
  placeholder: isColor ? '#rrggbb' : '—',
  handleChange: (next: string) => handleChange(key, next),
}) as never
```

No box, and no `handleCommit` — so `handleChange` is the field's only write channel. Meanwhile the panel's handler at `ensemble-editor.ts:3768` is `if (boxFor(key)) return;`, and `boxFor` = `boundIfSet(values, key, …)` returns a truthy leaf box for **any key the document already has**. Set field → guard fires → `updateFeature` never called → nothing written, nothing rendered, no error.

Reproduced by executing the real code paths: `values {texture:'/grid-10.svg'}` → `setValue('/other.svg'); commit()` → `writes: []`. With `values {}` → `writes: [['texture','/other.svg']]`. Unset fields write once; from the next panel rebuild (any selection change) the field is dead.

Blast radius, measured against the registered scene schemas: ten free-text/colour fields — `skybox.sunColor/duskColor/moonColor`, `fog.color`, `light.diffuse/specular`, `ground.color/texture`, `water.waterColor`, `clouds.color`. Shipped ensembles hit it on open: `static/ensembles/standard-scene.json` sets `ground.texture`, `pirate-cove.json` sets `light.diffuse` — precisely the fields the changelog's "strings are editable now, including colours" entry is written about.

Two corrections to the original report, neither changing the verdict: `fog.mode` and `terrain.surfaceType` are `enum` upstream, take the `select3d` branch, and **are** correctly bound. And `InputFieldOptions.value` is typed `string` in `tosijs-3d/dist/keyboard.d.ts`, so `inputField` cannot bind a box at all — the fix must read `(bound as {value}).value` and write `box.value`, or exempt unbound-widget keys from the editor's guard.

This is the same defect the diff's own comment at ~`ensemble-editor.ts:3663` describes catching and fixing for the *opposite* half of the condition. `src/editor/schema-panel.test.ts` asserts only widget SHAPE (`commit`/`isValid` keys) and never passes a `box`, so no test covers a keystroke reaching the document.

**Fix, and the re-review scope:** cheapest correct fix is to route the string branch through `handleCommit ?? handleChange`, or better, have `schemaWidgets` report which keys it actually bound so the editor's early-return is derived from that fact rather than re-derived from `boundIfSet` — the comment at 3663 already names re-deriving it as the failure mode. **The guard is shared by every widget branch: the remediation must not re-enable double-writes on the bound slider/select/toggle branches.** Add a test that a keystroke on a SET string property reaches the document.

Secondary, worth checking while in there (unverified): these panel `inputField`s are not added to `inputs`, so they sit outside the `ui.fieldGroup` that is the only `attach()` for DOM key routing. The pre-existing rename field has the same shape — either both are typable via a host route or both need the group.

## MAJOR (4) — confirmed; none blocks on its own, all should be fixed or explicitly deferred with the reason written down

### M1 — A feature config's keys are written verbatim onto DOM elements, so an ensemble file can execute script in the host page
`src/runtime/features-scene.ts:323` (and the `...cfg` spreads at 626, 780, 878, 991, 1015, 1189, 1227, 1261, 1298) · lens: **security** · **confirmed**

`updateAttrs` is `for (const [key, value] of Object.entries(cfg)) { if (element[key] !== value) element[key] = value }`, wired as `update:` for ten of thirteen features; tosijs element creators apply unknown keys as properties. Verified under happy-dom with this repo's own deps, and **execution confirmed in real Chromium via Playwright** (`RESULT: executed`):

```
b3dLight({intensity:0.9, innerHTML:'<img src=x onerror=BOOM>'})
  -> <tosi-b3d-light><img src="x" onerror="BOOM"></tosi-b3d-light>
```

`add()` appends to the live scene, so the handler fires. No gate on the way in: `parseEnsemble` is `JSON.parse` + `Array.isArray(pieces)`; `openFile`, `openSaved` and `<tosi-ensemble src>` all feed it straight through; `validate()` checks only that the feature NAME is registered, no schema sets `additionalProperties`, and no test feeds a hostile key. An author opening a shared `pirate-cove.ensemble.json` gets script in the editor page's origin, which holds every `ensemble:*` draft in localStorage — and the host app's session wherever the editor or `<tosi-ensemble>` is embedded.

Latent since v0.2.0, which is why it is major and not a blocker. Fix: filter to the feature's declared schema before it reaches an element — `registration.schema.properties` is already the exact allow-list `pick()` builds, and `src/runtime/place-mesh.ts:102` already builds its element from an explicit key list and is the pattern to copy. If the decision is instead "an ensemble is trusted code, not content", **that must be written down in SPEC.md/README next to `loadEnsemble` and `openFile`**, because the format's whole pitch is a document you share.

### M2 — The new `meshes-unchecked` honesty warning has a hole at PARTIAL library mount — the case `buildEnsemble` actually derives
`src/format/validate.ts:447` · lens: correctness · **confirmed**

`meshesByLibrary` only adds an entry for a library that returned names, so a two-library ensemble with one slow/404ing kit yields a Map of size 1. `build.ts:189` → `checkable` true; `validate.ts:447` → `unchecked` false; no warning. Reproduced end-to-end: a piece qualified `library:'kit-b'` with mesh `TOTAL-GARBAGE` produces **no problem at all**, and an unqualified piece whose mesh lives in kit-b produces a hard `{severity:'error', code:'unknown-mesh', message:'"barrel" is not in any mounted library'}` — the exact false accusation the module's own comment says the skip exists to prevent, arriving through the door marked *checked*.

The editor path is worse: `_meshNames()` flattens the Map into a single `Set`, and `knownMeshes()` ignores the piece's `library` qualifier when given a Set — so a partial mount false-positives QUALIFIED pieces too. `static/ensembles/city-block.json` is a shipped 4-library ensemble whose 20 mesh pieces are all library-qualified: one slow kit fills the panel with `unknown-mesh` errors about perfectly good content, with no warning.

One narrative correction: both bad outcomes are pre-existing v0.2.0 behaviour, not introduced by the diff. What is new is that the warning added to close this silence does not cover the case that actually happens, and the new `libraries` option — added so the message could name the non-answering libraries — is never reached when some answered and some did not.

Fix: make the check per-library. When `meshes` is a Map and `opts.libraries` names a library with no (or empty) entry, emit `meshes-unchecked` naming it, and suppress the union fallback for unqualified pieces while any declared library is missing. Add a test with a Map covering one of two declared libraries — `validate.test.ts:308-353` covers only `undefined`/empty-Set/populated-Set, and `build.test.ts`'s "names the libraries it asked" passes only because NOTHING answered.

### M3 — `_mountShelf()` calls `_renderChrome()` from inside `_renderChrome()`
`src/editor/ensemble-editor.ts:3037` (chain: 2862 → 3077 → 3037) · lens: correctness · **confirmed**

Deterministic, not racy. `_renderLibraryPalette` has exactly one caller, `_mountShelf()` is its first statement, and the new guard has no re-entrancy flag. The inner `_renderChrome` removes every panel, resets `_stackTop`, rebuilds all five; control returns to the outer `_renderLibraryPalette`, which `_addPanel`s its own palette, then `_renderProperties()` adds a second properties panel — 7 panels in the DOM, palette and properties doubled, for the whole shelf-load window. `_renderProperties` also does `this._detachFields?.(); … = group.attach()`, so the outer pass detaches the inner panel's `fieldGroup`: **a visible property panel whose inputs are wired to no keyboard** — this repo's own named cardinal sin, in exactly the window the new spinner exists to make honest.

The comment "the mount above may resolve synchronously from cache" describes something JS cannot do: `mountLibraries` is `export async function`, so its `.then` can never run before the next synchronous statement. The branch reads as rare and is certain. Live on the documented demo — `editor.md:43` passes a four-kit `libraries` shelf, so this fires the first time an author picks Insert and lasts the full CDN load of four GLBs. Self-heals when the mount's `.then` fires a clean render.

Fix: `queueMicrotask(() => this.isConnected && this._renderChrome())`, or a `_renderingChrome` flag turning a nested request into a post-pass re-render. Correct the comment while you are there.

### M4 — `floorplanDiff` pairs same-named records by array index
`src/runtime/scene-floorplan.ts:187` · lens: correctness · **confirmed**

`sceneFloorplan` sorts by `name` only and `Array.prototype.sort` is stable, so same-named records keep SCENE order — the ordering the adjacent comment itself calls non-visual. `floorplanDiff`'s `COUNT FIRST` guard ("matching them up individually would invent a pairing the scene never had") is honoured only on the unequal-count path; on equal counts the loop does `olds[i]` / `news[i]`. Reproduced against the shipped module — two meshes both named `barrel` at (0,0,0) and (10,0,0), created in the opposite order across a rebuild:

```
CHANGES [{name:'barrel',kind:'moved',before:[0,0,0],after:[10,0,0]},
         {name:'barrel',kind:'moved',before:[10,0,0],after:[0,0,0]}]
```

Two `moved` changes for a pixel-identical picture, against a module whose selling point is non-flaky signal. Latent today (the one consumer fence runs a unique-name scene, and its gate is `fixme`'d anyway) but the reorder is realistic in this stack specifically: `activeOnly` reads the post-cull draw list, library instances are created inside `lib.ready.then(...)` plus `whenMeshed`'s render-observer retry, and `getNames()` strips `.model`/`_primitiveN` which makes name collisions *more* likely. `scene-floorplan.test.ts`'s one duplicate case uses 3-vs-1, the unequal-count path, so the suite cannot see it.

This is newly-shipped public API exported from `src/index.ts`. Fix now, while it is cheap: compare same-name groups as position-keyed multisets, or sort within the name group by `at`/`size` before pairing. Add the missing test: same count, same positions, different creation order → no changes.

## Findings

### Minor

1. **[correctness + blast-radius, verified] Self-registering on connect overwrites a consumer's earlier feature of the same name.** `src/runtime/ensemble-element.ts:182-183`. `connectedCallback` now calls `registerSceneFeatures()` every time. That function only guards itself with its own `registered` flag (`src/runtime/features-scene.ts:742-755`). `registerFeature` is a plain `Map.set` (`src/format/registry.ts:281`). Suppose a consumer on 0.5.0 registered their own `fog` or `sun` and never called `registerSceneFeatures()`, which was optional then. The first `<tosi-ensemble>` that connects replaces their feature with the built-in and says nothing. That breaks the CLAUDE.md rule that a consumer's feature must be indistinguishable from a built-in. Few consumers will hit it: overriding a built-in is not documented, and the editor already does the same thing on connect (`src/editor/ensemble-editor.ts:850`). The blast-radius lens rated it a nit and correctness rated it minor; it is kept at minor here because a consumer's feature disappearing silently is the "nothing says so" class this project has paid for before. *Fix:* have the element's auto-registration only fill in names that are not registered yet (for example `registerSceneFeatures({ overwrite: false })`), or document the order in the CHANGELOG. Add a fresh-process fixture case for the override.
2. **[correctness, unverified] `_requestedSrc` is never reset.** `src/runtime/ensemble-element.ts:205`. Three cases: (a) `load(B)` followed by any attribute write refetches `src=A`; (b) setting src A, then '', then A again never refetches; (c) assigning `.ensemble` while a fetch is in flight is overwritten when the fetch resolves, because the setter does not bump `_loads`. *Fix:* make the setter and a cleared src count as a new request. Decide whether `load(url)` is public and should win over `src`. Add a test for (c).
3. **[correctness, unverified] Rebuilds from a reconnect or from `.ensemble` never mount libraries.** `src/runtime/ensemble-element.ts:236`. `mountLibraries` only runs inside `load()`, and only when the element is attached to a `tosi-b3d` at the moment the fetch resolves. So a move to a different `<tosi-b3d>`, a fetch that resolves while the element is detached, and a document with libraries assigned to `.ensemble` all rebuild without their libraries. The new docs claim a move rebuilds whatever the source, which goes further than this. The move test uses a document with no libraries. *Fix:* in `_sync`, mount libraries (the call is idempotent) before rebuilding, under the same ticket guard. Otherwise, narrow the docs claim. Add a move test that uses a document with a library.
4. **[correctness, unverified] The "a slower earlier src cannot overwrite a later one" test cannot fail.** `tests/ensemble-element.pw.ts:106`. All the documents involved have no libraries and are served locally, so the first request resolves first anyway. The CHANGELOG lists the race guard as fixed and checked, but it has no test that can fail. This is a missing test, so it does not block. *Fix:* use `page.route` to delay the first URL, and confirm the test fails with the `ticket !== this._loads` checks removed.
5. **[blast-radius, unverified] The fetch, mountLibraries, build path now exists three times, and each copy has different fixes.** `src/runtime/ensemble-element.ts:226`, `src/editor/ensemble-editor.ts:1569`, `src/runtime/build.ts:560`. Only the element has all three of: the `!response.ok` check, the stale-load guard, and the `error` event. The editor has no `ok` check, so a 404 shows up as an unhandled JSON parse rejection. `loadEnsemble` has no stale guard. *Fix:* write one runtime helper (`fetchEnsembleData(url, scene, isCurrent)`) and use it from all three places. The editor importing from the runtime is the allowed direction, so tree-shaking is unaffected. If this is deferred, record the decision to keep three copies.

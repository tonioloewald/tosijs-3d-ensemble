## Fix before the tag (verified majors)

- [ ] **Nested-object fields merge into a stale snapshot, so editing a second sub-field reverts the first.** `src/editor/schema-panel.ts:~560`. `merged = (k, v) => ({ ...current, [k]: v })` spreads the `current` value captured when the panel was built. `updateFeature` deliberately does not rebuild the panel on a value write, so editing `radar.boost.name` and then `range` writes the old name back. This is silent data loss in the exact case board #3352 fixed for Manta.
  *Fix:* keep a mutable local copy that each write updates (`current = merged(k, v)`), or read the live value through a getter or box.
  *Check that clears it:* a `schema-panel.test.ts` case that edits two sibling sub-fields in turn and asserts both survive (`{name:'aX', label:'bY'}`). It must fail when the fix is reverted. The reviewer's scratchpad probe already reproduces the bug.

- [ ] **Save overwrites the previously opened store document after New, Open file, openSaved or `load(src)`.** `src/editor/ensemble-editor.ts:1062`. `_storeId` and `_savedJson` are only ever set (lines 1052, 1068, 1085), never cleared. The `ensemble` setter (line 542) and `newEnsemble` (line 3148) leave them in place, so the Save button stays visible and `saveToStore()` writes the new document over e.g. `harbour.json`. The dirty mark and the Open picker also still point at harbour. With commit off (this site's config), nothing on disk can undo the overwrite.
  *Fix:* set `_storeId = null; _savedJson = null` in the `ensemble` setter and in `newEnsemble()`. `openFromStore` and `openRevision` already assign `_storeId` after the setter, so they keep working.
  *Check that clears it:* a unit test with a fake store: open id A, then New (and, separately, assign `ensemble`), then Save. The test asserts that A was not written and that Save is hidden or falls back to Save as. It must fail when the fix is reverted.
